# 베타1 사용 권한 요청 시 이름 입력 — 설계

## 배경

베타1 사용 현황을 확인해보니 승인된 6명이 전부 `id: 8786287796` 같은 텔레그램 숫자 id로만 식별된다. `allowed_users.json`/`pending_requests.json`은 신청 시점에 텔레그램 initData에서 받은 `username`(공개 아이디)과 `first_name`(텔레그램 프로필 이름) 두 필드만 저장하는데, 실제로는 이 두 필드가 비어 있거나 닉네임이라 "이 id가 현장에서 누구인지"를 운영자가 알아낼 방법이 없다.

`access_control.py`에는 이미 `username → first_name → user_id` 순으로 표시 이름을 고르는 `resolve_display_name()` 헬퍼가 있고, 이 값은 관리자 알림·`/stats`·`/authlog`·피드백 로그 등 운영자가 보는 화면 전부에서 재사용된다. 즉 표시 이름 소스 하나만 바꾸면 파급 범위는 이미 갖춰져 있다 — 문제는 그 소스가 텔레그램 프로필 값뿐이라는 것.

이 스펙은 사용자가 **직접 입력한 이름**(`display_name`)을 새 데이터 소스로 추가하고, `resolve_display_name()`의 최우선 순위로 끼워 넣는다.

## 목표

- 신규 사용 신청자는 관리자 승인 전에 이름을 답장으로 입력하고, 관리자는 이름이 붙은 상태로 승인/거절을 판단한다.
- 기존 승인자(현재 6명 포함)도 다음 미니앱 접속 시 1회, 사용을 막지 않는 선에서 이름을 요청받는다.
- 이름이 입력되면 관리자 알림·`/stats`·`/authlog`·피드백 알림 전부에 자동으로 반영된다(단일 헬퍼 수정).
- 신규 신청자가 답장을 하지 않아 승인 자체가 막히는 일이 없도록 타임아웃 안전망을 둔다.

## 비목표

- 이름 수정/정정 명령(`/setname` 등)은 만들지 않는다 — 잘못 들어간 값은 운영자가 데이터 파일을 직접 고친다(현재 규모에서 CRUD 명령을 만들 실익이 없음).
- 미니앱(웹뷰) 프론트엔드에 입력 폼을 추가하지 않는다 — 텔레그램 채팅 답장만으로 받는다.
- 실명 검증(신분증 대조 등)은 하지 않는다 — 사용자가 입력한 문자열을 그대로 신뢰한다.
- 자동 재알림(이름 답장을 N번 더 독촉)은 넣지 않는다 — 신규는 타임아웃 폴백 1회, 기존 승인자는 최초 1회 요청 후 끝.

## 아키텍처

### 데이터 구조 변경

`access_control.py`의 `_load`/`_save` 헬퍼를 그대로 재사용한다. 기존 2필드 스키마에 필드를 추가한다.

**`pending_requests.json`** (신규 신청자, 승인 전)
```json
{
  "123456789": {
    "username": null,
    "first_name": "철수",
    "display_name": null,
    "name_requested_at": "2026-08-06T21:00:00+09:00",
    "admin_notified": false
  }
}
```

**`allowed_users.json`** (승인된 사용자 — 신규 승인 시 pending에서 복사, 기존 6명은 소급 추가)
```json
{
  "8786287796": {
    "username": null,
    "first_name": "영기",
    "display_name": "백영기 대리",
    "name_asked_at": "2026-08-06T21:05:00+09:00"
  }
}
```

`name_requested_at`/`admin_notified`은 신규 신청 흐름 전용, `name_asked_at`은 기존 승인자 소급 흐름 전용이다 — 승인 시점에 `pending`의 `display_name`만 `allowed_users`로 복사하고 나머지 필드는 새로 시작한다.

### `api/access_control.py`

```python
def resolve_display_name(user_id, username=None, first_name=None, display_name=None):
    """display_name → username → first_name → str(user_id) 순.
    호출부는 allowed_users.json/pending_requests.json에서 읽은 display_name을 그대로 넘긴다."""

def is_valid_name_reply(text):
    """20자 이내, "/"로 시작하지 않음, 쉼표·물음표·마침표를 포함하지 않으면 True.
    문장형 답장(피드백 자유의견이 이름 요청과 겹쳐 들어온 경우 등)을 이름으로 잘못 저장하지 않기 위한 최소 방어."""

def is_awaiting_name(user_id):
    """이 user_id가 지금 "이름 답장 대기" 상태인지 판단.
    - pending_requests.json에 있고 display_name이 비어 있으면 True (신규 흐름)
    - allowed_users.json에 있고 display_name이 비어 있고 name_asked_at이 채워져 있으면 True (기존 소급 흐름)
    두 상태는 서로 다른 파일이라 동시에 겹치지 않는다."""

def record_name_reply(user_id, text):
    """is_awaiting_name(user_id)가 True일 때만 호출.
    pending 쪽이면 display_name 저장 후 관리자에게 "새 사용 신청" 알림 발송(admin_notified=True).
    allowed 쪽이면 display_name만 저장하고 별도 알림 없음."""

def sweep_stale_name_requests(timeout_minutes=30):
    """pending_requests.json을 훑어 admin_notified가 False이고
    name_requested_at으로부터 timeout_minutes 이상 지난 항목을 찾아
    "(이름 미입력)"으로 관리자 알림을 보내고 admin_notified=True로 표시.
    다른 웹훅 이벤트 처리 시작 지점과 /stats 핸들러에서 호출한다(별도 스케줄러 없음)."""

def maybe_ask_backfill_name(user_id):
    """allowed_users.json에서 user_id를 조회해 display_name이 비어 있고
    name_asked_at도 비어 있을 때만 이름 요청 메시지를 보내고 name_asked_at을 채운다.
    require_telegram_auth()의 모든 호출 경로에서 실행되므로 예외를 삼키고
    실패해도 API 응답에 영향을 주지 않는다(error_alert.py와 동일 원칙)."""
```

`register_pending_request()`는 승인 요청 시 즉시 관리자에게 알리던 것을 그만두고, 사용자에게 이름을 요청하는 메시지만 보내도록 바뀐다. 관리자 알림은 `record_name_reply()` 또는 `sweep_stale_name_requests()`에서만 나간다.

### `api/telegram_auth.py`

`require_telegram_auth()`가 `is_allowed(user_id) == True`를 확인한 직후, 딱 한 줄 추가:

```python
if is_allowed(user_id):
    access_control.maybe_ask_backfill_name(user_id)  # display_name 없고 name_asked_at 없을 때만, 실패해도 무시
```

`maybe_ask_backfill_name()`은 `error_alert.py`와 같은 예외 삼키기 패턴을 따른다 — 이름 요청 발송이 실패해도 미니앱 API 응답에는 절대 영향을 주지 않는다.

### `api/webhook.py` — 텍스트 메시지 우선순위 재정렬

`_handle_message()`의 분기 순서를 다음과 같이 바꾼다(기존 78-91번째 줄 로직 앞에 삽입):

```python
if access_control.is_awaiting_name(user_id):
    if access_control.is_valid_name_reply(text):
        access_control.record_name_reply(user_id, text)
        send_message(chat_id, f"감사합니다, {text}님으로 등록했습니다 🙌")
    else:
        send_message(chat_id, "이름만 간단히 입력해주세요 (예: 홍길동)")
    return

# ... 기존 관리자 명령(/stats, /revoke, /authlog, /broadcast_feedback) 분기 ...
# ... 기존 /start 분기 ...
# ... 기존 feedback_survey.handle_free_text 분기 ...
```

이름 대기 상태 체크가 관리자 명령·`/start`·피드백 자유의견보다 먼저 온다. `sweep_stale_name_requests()`는 웹훅 진입점(`_handle_message`/`_handle_callback_query` 최상단)에서 매 이벤트마다 가볍게 호출한다 — pending 목록이 비어 있으면 즉시 반환하므로 비용은 무시할 수준이다.

### 승인 콜백 (`_handle_callback_query`, action == "approve")

`add_allowed_user()` 호출 시 `pending.get("display_name")`도 같이 넘겨 `allowed_users.json`에 이름이 이어지도록 한다.

### 관리자 알림 문구

- 신규(이름 있음): `📩 새 사용 신청: 백영기 대리 (텔레그램: 철수, id: 123456789)`
- 신규(타임아웃 폴백): `📩 새 사용 신청: (이름 미입력) (텔레그램: 철수, id: 123456789)`
- 기존 승인자에게 보내는 이름 요청: `"안녕하세요! 베타 테스트에 참여해주셔서 감사합니다 🙏 피드백 정리를 위해 성함을 답장으로 알려주시겠어요? (예: 홍길동)"`

### 표시 반영 (`admin_stats.py`, `feedback_survey.py`)

`build_stats_message()`, `build_authlog_message()`, `feedback_survey._notify_admin()` 안에서 직접 `username`만 읽던 부분을 전부 `access_control.resolve_display_name(uid, username=..., first_name=..., display_name=...)` 호출로 교체한다. 로직 변경은 이 헬퍼 하나에만 있고, 나머지는 호출부만 바뀐다.

## 데이터 흐름 / 에지 케이스

- **신규 신청 → 이름 답장 → 관리자 알림 → 승인**: 정상 경로. `display_name`이 `pending`에서 `allowed`로 복사됨.
- **신규 신청 → 30분 무응답**: `sweep_stale_name_requests()`가 다음 웹훅 이벤트(다른 사용자의 것이어도 무방) 또는 `/stats` 호출 시점에 "(이름 미입력)"으로 관리자에게 알림. 이후 사용자가 뒤늦게 이름을 답장하면 `display_name`은 저장되지만 `admin_notified`가 이미 True라 추가 알림은 안 감 — 관리자는 승인/거절 시점에 `/stats` 등으로 다시 확인해야 함(재알림 없음은 의도된 절충).
- **기존 승인자 6명, 다음 접속 시 이름 요청**: `require_telegram_auth()`를 통과하는 모든 API 호출(문서 목록 조회든 생성이든)에서 한 번 걸릴 수 있는데, `name_asked_at`을 즉시 채우므로 같은 세션 안에서 여러 번 API를 호출해도 메시지는 1번만 나간다.
- **기존 승인자가 이름 요청과 피드백 자유의견 질문을 동시에 받는 경우**: 두 메시지가 겹쳐서 도착할 수 있는 좁은 창이 존재한다(둘 다 텔레그램 채팅 하나로 옴). 다음 텍스트 답장은 "이름 대기" 체크가 최우선이라 이름으로 먼저 소비된다 — `is_valid_name_reply()`가 20자 초과나 문장부호 포함 답장을 걸러내므로, 실제 피드백 문장(대개 그보다 길거나 쉼표·물음표를 포함)이 잘못 이름으로 저장될 가능성은 낮다. 걸러진 경우 원래 자유의견은 유실되고 사용자는 "이름만 간단히"라는 재안내를 받는다 — 드물고 되돌릴 수 없는 사고는 아니라고 판단해 이 이상 정교하게 막지 않는다.
- **텔레그램 발송 자체 실패**: `maybe_ask_backfill_name()`, `record_name_reply()`의 관리자 알림 발송 모두 예외를 삼키고 로그만 남긴다 — 미니앱/문서 생성 흐름에 영향 없음.

## 테스트 계획

기존 `test_clearance_checker.py`류의 순수 함수 단위 테스트 패턴을 따른다(텔레그램 발송은 모킹).

1. **이름 검증**: 20자 이내 일반 텍스트 → 통과. 21자 이상, `/`로 시작, 쉼표·물음표·마침표 포함 → 거부.
2. **신규 흐름 상태 전이**: `register_pending_request()` → `is_awaiting_name()` True → `record_name_reply()` → `admin_notified=True`, `is_awaiting_name()` False로 전환.
3. **타임아웃 폴백**: `name_requested_at`을 31분 전으로 세팅한 pending 항목에 `sweep_stale_name_requests()` 호출 → 관리자 알림 발송 확인, `admin_notified=True`로 갱신. 이미 `admin_notified=True`인 항목은 재발송 안 됨.
4. **기존 승인자 1회성**: `maybe_ask_backfill_name()`을 같은 user_id로 두 번 호출 → 메시지는 1번만 발송(`name_asked_at`이 이미 채워졌으므로).
5. **표시 이름 우선순위**: `display_name`/`username`/`first_name` 조합 4가지 케이스에서 `resolve_display_name()`이 올바른 값을 반환하는지.
6. **승인 시 이름 이어짐**: `pending`에 `display_name`이 있는 상태로 승인 콜백 처리 → `allowed_users.json`에 같은 값이 들어가는지.
7. **우선순위 회귀**: 이름 대기 상태가 아닌 사용자가 보낸 일반 텍스트는 기존처럼 `feedback_survey.handle_free_text()`로 흘러가는지(이번 변경이 기존 피드백 자유의견 경로를 깨지 않는지 확인).
