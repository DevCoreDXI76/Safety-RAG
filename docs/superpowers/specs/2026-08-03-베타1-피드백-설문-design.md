# 베타1 텔레그램 인앱 피드백 설문 — 설계

## 배경

베타0에서는 claude.ai 아티팩트로 만든 별도 폼으로 피드백을 받았다. 이 폼은 claude.ai 계정 로그인/공유 설정에 걸려 계정이 없는 테스터는 아예 접근이 안 됐고, 결국 폼 내용을 카카오톡으로 옮겨 받는 우회가 발생했다. 베타1은 18~20명 규모로 테스터가 늘어나므로, 계정 생성이 전혀 필요 없는 채널로 피드백을 받아야 한다.

Safety-RAG는 이미 텔레그램 봇(`api/webhook.py`, `api/telegram_bot.py`, `api/access_control.py`)을 통해서만 사용되는 제품이다 — 테스터 전원이 이미 텔레그램 계정을 갖고 있고, 봇과 대화하는 것 자체가 제품 사용 경험의 일부다. 별도 도구를 도입하는 대신 이 봇 안에 피드백 수집 기능을 내장한다.

설계 과정에서 세 가지 실패 모드를 순서대로 짚었고, 이 스펙은 그 결론을 반영한다:

1. **"문서 3종을 모두 만들어야 트리거"는 이탈자를 영원히 놓친다** → 트리거 기준을 문서 타입별 "최초 1회 생성"으로 낮춘다.
2. **"매 생성마다 설문을 다시 보내면 테스터가 싫어한다"** → 문서 타입별로 이미 트리거된 적 있으면(완료 여부 무관) 재발송하지 않는다.
3. **"생성 자체를 막아서 응답을 강제하면 어떨까"는 리스크가 더 크다** → 베타1이 검증하려는 핵심(위험성평가표→작업계획서→TBM일지 순서 안내를 따라 매끄럽게 넘어가는지)을 설문이 가로막아 관찰 대상을 오염시키고, 현장 근로자 특성상 막히면 응답 대신 이탈할 위험이 크다. 대신 문서 타입별 최초 생성 시 **비차단(non-blocking)** 으로 짧은 질문 1개만 던지는 절충안을 택한다.

## 목표

- 계정 생성 없이, 이미 봇을 쓰고 있는 테스터 전원이 추가 행동 없이 피드백을 받을 수 있다.
- 문서 타입(위험성평가표/표준 작업계획서/TBM 일지) 각각의 **최초** 생성 직후에만, 그 문서 경험에 대한 짧은 질문을 던진다. 2번째·3번째 반복 생성 때는 묻지 않는다.
- 질문은 비차단이다 — 응답 여부와 무관하게 다음 문서 생성은 항상 가능하다.
- 응답은 `user_id`뿐 아니라 표시 이름(username 또는 first_name)과 함께 로그로 남아, 나중에 "누구의 응답인지" 바로 알 수 있다.
- 응답이 들어올 때마다 관리자(사장님) 텔레그램으로 실시간 전달된다.
- 트리거됐지만 끝내 응답하지 않은 사람을, 게이트 임박 시 관리자가 수동으로 한 번 더 찔러볼 수 있는 안전망이 있다.

## 비목표

- 문서 3종을 모두 완료했는지 확인하는 것 자체는 이 설문의 트리거 조건이 아니다(각 문서 타입은 독립적으로 트리거됨).
- 자동 재알림(응답 안 하면 N일 뒤 봇이 알아서 다시 찌르는 것)은 넣지 않는다 — 안전망은 관리자 수동 명령(`/broadcast_feedback`)으로만 제공한다.
- Notion 연동, 외부 설문 도구 연동은 하지 않는다. 응답은 로컬 JSONL 파일에 남긴다(기존 `ab_test_results_*.jsonl` 패턴과 동일).
- Q3(형식 선호)는 이제 3형식(PDF/XLSX/HWPX)을 모두 제공하므로 묻지 않는다.

### 상태 파일: `data/feedback_state.json`

`access_control.py`의 `_load`/`_save` 헬퍼를 재사용한다. user_id → 문서 타입 3개 각각의 진행 상태.

```json
{
  "123456789": {
    "위험성평가표": {
      "triggered_at": "2026-08-05T10:00:00+09:00",
      "answers": {"q1_quality": "조금만 수정하면 됨"},
      "completed": true
    },
    "표준 작업계획서": {
      "triggered_at": "2026-08-05T10:20:00+09:00",
      "answers": {},
      "completed": false
    }
  }
}
```

트리거 조건은 정확히 하나: **`user_id`의 해당 `document_type` 키가 상태 파일에 아예 없을 때만** 트리거한다. `completed`가 `false`여도 키가 이미 있으면 재발송하지 않는다 — "응답을 안 했다"와 "이미 말을 건 적 있다"를 구분하지 않는다.

체크포인트 1("위험성평가표")과 2("표준 작업계획서")는 질문이 1개뿐이라 버튼 1번으로 바로 `completed: true`가 된다. 체크포인트 3("TBM 일지")만 질문 2개 + 자유의견의 3단계라, "이 user_id가 지금 TBM 체크포인트의 자유의견을 기다리는 중인가"를 판단할 별도 필드(`awaiting_free_text: true`)가 필요하다. 세 체크포인트는 서로 다른 `document_type` 키를 쓰므로 동시에 진행 중이어도 상태가 섞이지 않는다.

### 표시 이름 — 승인 시점에 이미 있는 정보를 안 흘리게 고친다

현재 `api/access_control.py`의 `add_allowed_user(user_id, username=None)`는 신청 시점에 받아둔 `first_name`을 승인 단계로 넘기지 않고 버린다([api/webhook.py:113-114](../../../api/webhook.py#L113-L114)). 많은 테스터가 텔레그램 공개 `username`(@아이디)을 설정하지 않으므로, 이 상태로는 `user_id` 숫자만 남는 사람이 다수 생긴다.

- `add_allowed_user`가 `first_name`도 같이 저장하도록 수정 (`api/webhook.py`의 승인 콜백에서 `pending.get("first_name")`도 같이 넘김).
- 피드백 로그 기록 시 `username or first_name or str(user_id)` 순서로 표시 이름을 붙인다 — `register_pending_request`에 이미 있는 폴백 로직과 동일한 순서.
- 테스터 쪽에는 어떤 추가 입력도 요구하지 않는다.

### 트리거 연결 지점: `api/routes.py`의 `generate()`

레코드 저장이 성공한 직후, `feedback_survey.maybe_trigger_checkpoint(user_id, document_type)`를 한 줄 호출한다. 이 호출에서 발생하는 예외는 절대 `/generate` 응답에 영향을 주면 안 된다(`error_alert.py`와 동일하게 예외를 삼키고 로그만 남김).

### 웹훅 연결 지점: `api/webhook.py`

- 콜백 쿼리 핸들러(`_handle_callback_query`)에 `feedback:` 접두사 분기 추가 — 기존 `approve`/`reject` 분기와 같은 자리에 나란히 둔다.
- 일반 텍스트 메시지 핸들러에서, 기존 `/start` 외 텍스트를 무시하던 분기 **앞에** "이 user_id가 지금 TBM 체크포인트 자유의견 대기 중인가"를 먼저 확인하는 체크를 추가한다.
- 관리자 전용 명령으로 `/broadcast_feedback` 추가 — `/stats`, `/authlog`, `/revoke`와 같은 패턴(관리자 `chat_id` 확인 후 처리).

### 데이터 로그: `data/beta1_feedback.jsonl`

체크포인트가 완료될 때마다(TBM처럼 다단계인 경우 전체 3단계가 끝났을 때) 한 줄 append. 문서 3종을 다 안 써도 완료된 체크포인트만큼은 로그에 남는다.

```json
{"user_id": 123456789, "display_name": "백양기", "document_type": "위험성평가표", "answers": {"q1_quality": "조금만 수정하면 됨"}, "completed_at": "2026-08-05T10:01:30+09:00"}
```

### 관리자 알림

체크포인트가 완료될 때마다 `send_message(ADMIN_TELEGRAM_USER_ID, ...)`로 요약을 즉시 전달한다. 테스터 20명 × 체크포인트 3개 규모라 `error_alert.py`처럼 쿨다운을 둘 필요는 없다 — 매번 보내도 스팸 수준이 아니다.

## 데이터 흐름 / 에지 케이스

- **문서 3종을 다 안 만든 사람**: 만든 만큼의 체크포인트만 트리거되고, 그만큼만 로그에 남는다. 데이터 손실이 아니라 "부분 응답"으로 취급한다.
- **같은 문서 타입을 여러 번 생성**: 두 번째부터는 상태 파일에 이미 키가 있으므로 트리거 안 됨.
- **TBM 체크포인트 중간에 다른 문서를 또 생성**: 체크포인트는 `document_type`별로 독립이라, TBM의 자유의견 대기 상태와 무관하게 다른 문서 생성은 항상 가능하다.
- **자유의견을 안 쓰고 싶은 경우**: "생략하고 완료" 인라인 버튼으로 바로 완료 처리한다 — 텍스트 입력을 강제하지 않는다.
- **텔레그램 발송 자체가 실패**(네트워크 오류 등): `maybe_trigger_checkpoint`가 예외를 삼키고 로그만 남기며, 상태 파일에도 `triggered_at`을 기록하지 않아 다음 생성 시 재시도 여지를 남긴다(발송 성공 여부와 무관하게 "시도했다"로 확정 저장하지 않음).
- **first_name도 username도 없는 극히 드문 경우**: `user_id`를 그대로 표시 이름으로 사용한다(기존 `register_pending_request`의 폴백과 동일).

## 안전망: `/broadcast_feedback`

관리자 전용 명령. 상태 파일을 훑어 `triggered_at`은 있지만 `completed`가 `false`인 `(user_id, document_type)` 조합만 골라, 해당 체크포인트의 (진행 중이던 단계부터) 질문을 재발송한다. 자동 스케줄은 없다 — 게이트(2026-09-08) 임박 시 관리자가 필요하다고 판단할 때 1회성으로 실행한다.

## 테스트 계획

기존 `test_clearance_checker.py`, `test_worktype_citations.py`류의 순수 함수 단위 테스트 패턴을 따른다(텔레그램 실제 발송은 모킹하거나 호출 여부만 확인).

1. **트리거 1회성**: 같은 `(user_id, document_type)`으로 `maybe_trigger_checkpoint`를 두 번 호출하면 두 번째는 아무 것도 하지 않음(상태 파일에 키가 이미 있으므로).
2. **문서 타입 독립성**: 한 `user_id`가 세 문서 타입을 각각 생성하면 세 체크포인트가 모두 독립적으로 트리거됨.
3. **TBM 3단계 상태 전이**: Q2 응답 → Q4 질문으로 전환 → Q4 응답 → 자유의견 대기 상태 진입 → 텍스트 입력 또는 스킵 버튼으로 `completed: true` 전환.
4. **표시 이름 폴백**: `username` 있음 / `username` 없고 `first_name`만 있음 / 둘 다 없음 세 케이스에서 로그에 올바른 표시 이름이 남는지.
5. **`/generate` 격리**: `feedback_survey` 쪽에서 예외가 나도 `/generate`가 정상 응답을 반환하는지(모킹으로 강제 예외 발생시켜 확인).
6. **`/broadcast_feedback` 대상 선정**: `completed: false`인 항목만 골라내는지, `completed: true`인 항목은 제외되는지.
